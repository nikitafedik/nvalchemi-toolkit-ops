# Benchmarks

Performance benchmarks for ALCHEMI Toolkit-Ops GPU kernels, covering both
the **Torch** and **JAX** backends. These pages present scaling behaviour
across system sizes, constant-workload sweeps, and batch-scaling modes for
each module.

```{toctree}
:maxdepth: 1

```

## Methodology

### Timing

| Backend | Mechanism | Details |
|---------|-----------|---------|
| **Torch** | CUDA Events | `start_event.record()` / `end_event.record()` around the kernel call, then `torch.cuda.synchronize()`. No host-side sync inside the timed loop. |
| **JAX** | Wall-clock + `block_until_ready` | `time.perf_counter()` before and after the kernel; `jax.block_until_ready(result)` flushes the queued work. Rows record the exact `timing_method`, including serial fallback paths where used. |

The shipped benchmark YAMLs use the publication timing protocol by default:
three warmup iterations and ten timed iterations on the full benchmark grid.
Both values are configurable via `parameters.warmup_runs` and
`parameters.timing_runs`, or via the shared `--warmup-runs` / `--timing-runs`
CLI flags. The reported value is the mean steady-state time per call after
warmup/compile/load work is excluded.

### Scaling modes

Each benchmark page presents three scaling modes:

System Size Scaling
: Fix batch size = 1, sweep the number of atoms per system.

Constant Workload
: Fix total atom count, sweep batch size (fewer atoms per system, more
  systems). Reveals per-launch overhead.

Batch Scaling
: Fix atoms per system, sweep batch size. Reveals how well the kernel
  amortises fixed overhead across systems.

### Systems

| System | Source | Description |
|--------|--------|-------------|
| **CsCl** | Programmatic supercell builder in `benchmarks.suite_systems` | BCC CsCl supercells (2 atoms/unit cell, cubic 4.119 Å). |
| **NH₃** | PDB files generated by `benchmarks/nh3/generate_pbc_pdbs.sh` (requires [packmol](https://m3g.github.io/packmol/)) | Periodic ammonia boxes at powers-of-two atom counts. |

```{warning}
These results are intended to be indicative _only_: your actual performance
may vary depending on the atomic system topology, software and hardware

```

```{note}
**Precision**: NL and DFT-D3 use ``float32``; electrostatics
(PME / Ewald) use ``float64``; charges are always ``float64``.

**Missing plotted points** are rows where the benchmark wrote `success=False`
with a concrete `error_type` such as `OutOfMemoryError`, `SkippedByPolicy`,
or `SkippedAfterOOM`. Hardware-dependent OOM limits are not hardcoded into the
suite; failed and skipped rows remain in the CSVs and are omitted from plots.
```

## Running the full suite

The three modules share a single entry point,
``benchmarks.benchmark_suite``, which loads each per-module
``benchmark_config.yaml`` and dispatches in-process. Run from the
repository root:

```bash
# All three modules, Torch backend (default)
python -m benchmarks.benchmark_suite --benchmark all \
    --run-dir docs/benchmarks/benchmark_results

# All three modules, JAX backend
python -m benchmarks.benchmark_suite --benchmark all --backend jax \
    --run-dir docs/benchmarks/benchmark_results

# Or a subset:
python -m benchmarks.benchmark_suite --benchmark nl d3 --backend torch
```

### Useful controls

The shared benchmark flags work both through `benchmarks.benchmark_suite` and
through the per-module runners:

- `--method` / `--methods` restricts the run to named APIs such as
  `naive_tile`, `cell_list_pair_centric`, `dftd3`, `pme`, or `ewald`.
- `--dry-run` prints the expanded plan without allocating GPU memory.
- `--list` is an alias for the expanded no-allocation plan, and `--count`
  prints only the planned row counts.
- `--max-total-atoms N` writes `SkippedByPolicy` rows for concrete cases above
  `N` atoms before allocation.
- `--d3-params-path PATH` points D3 benchmarks at a pre-seeded
  `dftd3_parameters.pt` file. This is useful on clusters where scratch is
  required and outbound internet is unavailable.

Suite-only plotting controls:

- `--plot-only RESULTS_DIR` rebuilds plots from existing CSVs without running
  benchmarks.
- `--plots time throughput memory` restricts which plot panels are regenerated.

`--backend warp` is currently supported for neighbor-list benchmarks only;
use `--backend torch` or `--backend jax` for D3 and electrostatics.

When Torch and JAX are written to the same docs directory, each runner replaces
rows for the backend being rerun while preserving rows from the other backend.
That avoids mixing unrelated rows while still producing unified CSVs for the plots.

### Wall-time on NVIDIA H100 80GB HBM3

Documentation regeneration uses the full reportable benchmark grid shown on
these pages. There is no separate reduced documentation-only run. Runtime is
hardware-dependent; run `--dry-run` first to inspect the expanded row count
before committing GPU time.

The shipped H100 results were produced as scheduler shards using the same
3 warmups + 10 timed runs and the same YAML grids as a single reportable run.
The CSVs record per-row timings, not scheduler wall-clock time; keep scheduler
logs or `RUN_LOG.md` artifacts with any PR report that quotes elapsed shard
times. Queue wait and one-time environment setup should be reported separately.

```{note}
For JAX runs, the suite sets `JAX_ENABLE_X64=1` when needed and defaults
`XLA_PYTHON_CLIENT_MEM_FRACTION=0.95` before importing JAX unless the user has
already configured XLA memory behavior. If `XLA_PYTHON_CLIENT_PREALLOCATE` is
unset, the suite prints a one-line allocator note before the first JAX import;
set `XLA_PYTHON_CLIENT_PREALLOCATE=false` explicitly if you prefer on-demand
allocation over the default preallocator. A persistent
`JAX_COMPILATION_CACHE_DIR` can reduce repeat-run compile overhead; shipped CSV
rows report steady-state timings with compile/warmup excluded.
```

On clusters, route caches to scratch explicitly before launching a run:

```bash
export XDG_CACHE_HOME=/scratch/$USER/nvalchemiops-cache
export WARP_CACHE_PATH=/scratch/$USER/nvalchemiops-warp-cache
export TORCH_EXTENSIONS_DIR=/scratch/$USER/nvalchemiops-torch-extensions
export PYTORCH_KERNEL_CACHE_PATH=/scratch/$USER/nvalchemiops-pytorch-kernels
export JAX_COMPILATION_CACHE_DIR=/scratch/$USER/nvalchemiops-jax-cache
export MPLCONFIGDIR=/scratch/$USER/nvalchemiops-mpl-cache
```

The D3 parameter cache follows `XDG_CACHE_HOME` when the default
`~/.cache/nvalchemiops/dftd3_parameters.pt` path is used. `RUN_LOG.md` records
these cache variables for each suite run. On offline clusters, pre-populate
`$XDG_CACHE_HOME/nvalchemiops/dftd3_parameters.pt` on scratch or pass
`--d3-params-path /scratch/$USER/.../dftd3_parameters.pt`.

For a reportable cluster run that keeps caches, virtual environments, logs, and
results off the home filesystem, set an explicit scratch root and use the helper:

```bash
cd benchmarks/nh3
printf '1-11\n' | bash generate_pbc_pdbs.sh
cd ../..

BENCHMARK_SCRATCH=/scratch/$USER/nvalchemiops-benchmarks \
    bash benchmarks/run_reportable_suite.sh --backend both
```

The helper runs the same full reportable NL/D3/EL grid with 3 warmups and
10 timed runs, and does not set `--max-total-atoms` or any hardware-specific
skip limits. Non-dry reportable runs preflight the generated NH3 PBC files from
the shipped YAML atom counts so missing inputs fail before benchmark CSVs are
written.

To reduce wall time without changing the reportable workload, shard the helper
by benchmark module, system, and scaling mode. Each shard should write to a
separate scratch output directory (or to a scheduler-managed merge directory),
then run plotting once after the CSVs are collected:

```bash
RESULT_DIR=/scratch/$USER/nvalchemiops-benchmarks/results/nl-cscl-constant_workload
BENCHMARK_SCRATCH=/scratch/$USER/nvalchemiops-benchmarks \
    bash benchmarks/run_reportable_suite.sh --backend both \
    --benchmark nl --system cscl --mode constant_workload \
    --output-dir "$RESULT_DIR" \
    --no-plot

python -m benchmarks.benchmark_suite \
    --plot-only /scratch/$USER/nvalchemiops-benchmarks/results/merged \
    --plots all
```

Sharding is a scheduling choice only: it uses the same YAML grids and the same
3 warmups + 10 timed runs as the single-process helper. It is useful on clusters
because JAX compilation and lowering can dominate wall-clock time even though
the CSV timing columns report steady-state kernel time with compile/warmup
excluded.

By default the helper runs `uv sync --extra torch --extra jax --group docs`,
then installs the benchmark-only runtime helpers `pyyaml` and `nvidia-ml-py`
into the same environment. It intentionally does not use `uv sync --all-extras`
because the project declares mutually exclusive CUDA extras. Override
`UV_SYNC_ARGS` and `BENCHMARK_PIP_PACKAGES` when a site needs a different CUDA
stack or a prebuilt environment.

If the scratch cache does not already contain D3 reference parameters and the
cluster cannot reach the Grimme parameter archive, provide a scratch-local
parameter file explicitly:

```bash
BENCHMARK_SCRATCH=/scratch/$USER/nvalchemiops-benchmarks \
    bash benchmarks/run_reportable_suite.sh --backend both \
    --d3-params-path /scratch/$USER/nvalchemiops-cache/nvalchemiops/dftd3_parameters.pt
```

For a no-allocation check, use `--dry-run` to confirm the expanded full-grid
plan before launching the reportable run.
